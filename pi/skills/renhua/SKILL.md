# 人话

让读者直接知道：谁做了什么，在什么条件下，有什么结果。默认使用清楚的书面语，保留作者的判断和专业术语。

## 任务入口

- **改写文字**：用户提供文本并要求改写，默认只返回修订稿。
- **审查项目**：用户要求 review、审查、检查或诊断，默认只报告问题；要求修改、修复或直接处理时才编辑文件。先完整读取 [REPOSITORY.md](REPOSITORY.md)，按其中的方法清点和验证。
- 用户指定的范围优先。项目内未指定范围时审查当前项目；当前位置无法确定项目根目录时，先询问路径，不把整个主目录当项目扫描。

## 执行步骤

### 1. 确认范围和语境

确定审查对象、读者、用途和是否允许修改。阅读完整段落及必要上下文；代码注释要对照实现，页面文案要对照所在组件和交互。

**完成标准**：每个待处理对象都有明确范围和用途；项目任务已建立文件清单，不能用搜索命中数量代替覆盖范围。

### 2. 保留原意

在工作记录中标出原文的事实、判断、经历和行动要求，只记录原文包含的内容。特别核对数字、单位、日期、名称、条件、否定、因果、确定程度及工作状态。

含义不明时保留原句并标为待确认。原因尚未确认时写“原因未查明”；已有的假设保留为假设，不能改成已确认的解释。未提供的数据、经历、引文和结论不予补写。

**完成标准**：每处拟修改文字的原意可追溯；歧义已标出，没有靠猜测补全的事实。

### 3. 按表达规则逐处处理

先删除不承载信息的开场、承接和重复总结，再调整句子。每处修改都要解决具体理解问题；原本清楚的文字保持不变。只审查时生成建议稿，不写入文件。

**完成标准**：范围内每个自然语言片段都已对照下列规则检查；发现的问题都有修订稿或待确认原因。

### 4. 验证并交付

逐处比较原文和修订稿，复核第 2 步保留的信息，再通读修订后的完整段落。项目任务还须完成参考文件中的结构与行为检查。

**完成标准**：所有改动都通过语义复核；项目清单无未说明的遗漏，未解决问题和未执行的检查已明确列出。

## 表达规则

### 直接陈述

从事实、问题、动作或判断起句，删除只负责提示“这里有洞察”的词语及复述上一段的总结。

- “核心在于保证数据质量” → “分析前需要校验数据来源和更新时间。”原文支持这些校验项时才这样具体化；否则写“分析依赖数据质量”。
- “别急着问模型，先看数据” → “数据有误时，模型分析也可能出错。”
- “我的结论是：这个方案……” → “这个方案……”。具体清单可以用冒号。

将“不是 A，而是 B”“是 X，不是 Y”“不仅 A，更 B”等修辞对比改为直接陈述。A 中含有事实、排除条件或纠错信息时，用独立句保留；普通否定、真实比较和逻辑条件照常表达。

### 明确指代和比较

指代不明时补出具体对象，如“这篇论文”“该测试结果”。上下文已明确的代词可以保留。

比较要交代对象和维度。“更适合”“更自然”“差距拉开了”若没有依据，保留为作者有限的主观判断，或标为待确认；不能替作者发明指标。

### 拒绝技术翻译腔与生造直译

英文术语往往有多重含义，禁止脱离软件工程、数据科学和学科实际，机械套用字典第一义项或生活实物词汇。用专业、自然的行业书面语替换字面直译。

- **测试数据（fixture）**：不要直译为“夹具”。改为“测试数据 / 预设测试数据 / 静态数据”；代码路径 `fixtures/` 保留英文。
- **数据结构与格式（contract / schema）**：不要译为中二腔的“契约”。改为“数据模型 / 数据格式规范 / Schema / 接口定义”。
- **表格文件（workbook）**：不要生硬直译为“工作簿”。改为“Excel 数据表 / 数据表格文件 / 原始数据表”。
- **数据内容（payload）**：不要使用航天直译词“有效载荷 / 载荷”。改为“数据内容 / 请求内容 / 样本数据结构 / 结果数据”。
- **来源记录（registry）**：不要在数据管理中使用行政词“登记”。改为“记录 / 收录 / 来源清单 / 元数据列表”。
- **处理流程（pipeline / scaffolding）**：不要使用工业比喻“管线 / 脚手架”。改为“处理流程 / 任务链 / 基础框架 / 辅助测试代码”。

### 消除伪术语与空洞黑话

禁止使用小圈子缩写暗号、内部生造简称和空洞的互联网大厂套话。让读者不需猜测暗号，直接获取事实。

- **拒绝圈内暗号**：不要把 ground truth 缩写成“金标”（改为“标准答案 / 参考真值 / 基准答案”）；不要把 self-proving 缩写为“自证”（改为“循环论证 / 标签循环依赖”）；不要把 blind / critique 模式生造为“盲答 / 批审”（改为“独立作答 / 证据审查”）；不要把 error causes 写作日式生造词“错因”（改为“错误原因 / 错误分类”）；不要把 disposition 写作“处置”（改为“处理意见 / 处理方案 / 记录”）。
- **去除大厂空洞大词**：删除或具体化“闭环、沉淀、赋能、抓手、心智、底座”。技术文档要陈述具体的系统链路与状态（如“从评测到训练的完整链路”而不是“建立闭环”；“已形成定稿 / 已归档”而不是“已沉淀”）。
- **区分学科真实术语与过程黑话**：保护学科真实科学用语，禁止盲目一刀切。化学中的“沉淀反应（precipitation）”、数学物理中的“数值收敛（convergence）”、材料力学中的“面载量/载荷（loading）”属于严格科学术语，必须精准保留；仅消除将它们作为比喻用在工作流程和软件逻辑中的套话。

### 使用标准术语和中性名称

优先使用项目术语表和行业通用术语。保留 API、token、cache、checkpoint 等准确名称；面向非专业读者时，按已有上下文补充简短解释。

严禁将自动化算法、评测机制和大模型拟人化为“裁判 / 裁判员 / 裁定”。评测体系是客观规则，统一使用中性名词：“自动评分模型 / 评分机制 / Judge 评分 / 评分细则校准 / 审核判定”。

标题、表头和状态使用中性名称，如“问题”“实验设置”“影响”“结果”“已完成”“进行中”“结论待定”。同一概念和状态在全文使用同一称呼。

### 说明实际对象和结果

把比喻、拟人、夸张及口号改为其对应的对象、动作或可观察结果。已有标准术语、正式名称和不可改写引文按原样保留，必要时在外部解释。

- “8 个不同血统的模型” → “8 个不同基座的模型”。
- “误差范围还盖着基准线” → “置信区间与基线重叠”。仅在原文所指确为置信区间时使用。
- “量规” → 教育测量生僻词，在模型评测中一律改为“评分细则 / 评分标准 / 评分规则 (Rubric)”。
- “上下文燃料”“能力飞轮”等表达，须先确定实际指代；无法确定就标为待确认。

### 使用清楚的书面语

拆开主语变化、条件堆叠和多层修饰的长句。优先使用明确动词，保留读者理解所需的条件，不以固定字数截短句子。

默认将俚语、圈内黑话和刻意口语化表达改为普通书面语，如“白跑”改为“无效运行”。作者的第一人称、立场和不确定性仍需保留。用户明确要求个人帖文或口播时，允许自然口语，继续执行准确性要求。

已完成的测试使用“测了”“完成了”；计划使用“接下来将”。事实叙述、建议和后续计划分别表达。

### 格式服务于内容

保留原文语言及必要结构；英文等其他语言按同样的清晰表达原则处理，不擅自翻译全文。

表格条目可以只报告现象，无需每条补上数字或结论。技术文档保留必要列表、代码块和表格。公共帖文默认使用短段落，不额外添加 emoji、标签、编号或劝告式结尾。

## 交付格式

- **文字改写**：只给修订稿；存在影响原意的歧义时，另附最少的待确认事项。
- **表达诊断**：引用原句，指出具体理解问题并给建议稿。短文只列实际发现的问题，不为凑数量添加问题。
- **项目审查或修改**：给出覆盖统计、问题或改动位置、验证结果和未解决事项。每项包含 `路径:行号`、原句、问题、建议或实际修订；大量同类问题可归组，但每个位置仍须可追溯。
